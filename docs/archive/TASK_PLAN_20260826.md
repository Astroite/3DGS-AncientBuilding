## 致密化窗口随规模放大（本次修订的核心）

splatfacto 的 `stop_split_at` 默认 15,000 步，**致密化到这一步就停止**，之后只是在精修一组固定的高斯。这个默认值是按 1,000 张量级的数据集调的，而 90 秒基准恰好是 1,080 张，所以基准跑得很好。

问题在于这个阈值是**步数**，不是**覆盖度**：

| | 透视图 | `stop_split_at` | 致密化期间每张图被采样 |
| --- | ---: | ---: | ---: |
| 90 秒基准 | 1,080 | 15,000 | **13.9 次** |
| 427 秒不调整 | 5,128 | 15,000 | **2.9 次** |

也就是说，如果照搬 15,000，大部分区域的高斯**根本来不及累积足够的位置梯度去分裂**。结果不是"精修不足、细节软"，而是**几何压根建不起来**。原规划把这件事描述为"平均训练采样次数约为基准的 21%"，那个说法只覆盖了精修，漏掉了更要命的致密化。

流水线现在**从配置里的视图数自动推导**整个致密化调度，保持每张图的采样次数不变：

| 参数 | 90 秒基准（1,080 张） | 本任务（5,128 张） |
| --- | ---: | ---: |
| `warmup_length` | 500 | 2,374 |
| `stop_screen_size_at` | 4,000 | 18,993 |
| `stop_split_at` | 15,000 | 71,222 |
| 每张图采样次数 | 13.9 | 13.9 |

要点：

- **1,080 张时推导结果与 Nerfstudio 默认值逐字相同**，所以已验证的基准运行行为完全没变。
- 推导只依赖 `frame_count × images_per_equirect`，这两个值本来就在配置哈希里，因此"同一个哈希 = 同一个模型"的保证仍然成立，**不需要新增配置项，也不会让已有的运行清单失效**。
- 始终保留精修尾巴：`stop_split_at` 不会超过 `max_iterations` 的 75%。本次 71,222 < 75,000，留下约 28,800 步精修。
- 无需在命令行传任何参数，自动生效；实际值会写进 `metrics.train.densification`。

**这仍是一个未经端到端验证的组合。** 71k 步致密化意味着高斯数量可能显著超过基准的 878,467，直接影响显存与 checkpoint 体积（见下）。这是本次运行最需要盯的一项。

## 时间预算（按实测重算）

原规划的预算基于优化前的数据，阶段构成已经完全不同。基准运行 `20260825T062740Z-46f434b6` 的实测分解（1,080 张透视图）：

| 步骤 | 实测 | 占重建 |
| --- | ---: | ---: |
| 特征提取 | 1.28 分钟 | 2.8% |
| 时序匹配 | 7.11 分钟 | 15.4% |
| 同帧跨视图匹配 | 0.32 分钟 | 0.7% |
| **mapping** | **34.26 分钟** | **74.3%** |
| rig BA + 转换 | 约 3 分钟 | 6.8% |
| 重建合计 | 46.1 分钟 | |

据此外推到 5,128 张：

| 阶段 | 预计耗时 | 依据 |
| --- | ---: | --- |
| 导入与预处理 | 3–5 分钟 | 线性 |
| 人像遮罩与 QA | 45–55 分钟 | 线性（基准 574 秒） |
| 特征 + 匹配 + 跨视图 | 40–45 分钟 | 线性 |
| **COLMAP mapping** | **2.7–6 小时** | **超线性，见下** |
| rig BA + 转换 | 15–30 分钟 | |
| 3DGS 训练（100k） | 4.2–6 小时 | 每步 144 ms 起，高斯变多会变慢 |
| 导出（含剔除） | 5–10 分钟 | |
| **总计** | **约 9–14 小时** | |

mapping 是唯一的大不确定项。增量式 SfM 的代价随注册图数超线性增长，34.26 分钟 × 4.75 的线性外推给出 2.7 小时，按经验的 n^1.3–1.5 则是 4.3–5.9 小时。**手上没有干净的缩放数据点**，所以这个区间是估计而非测量，实际值应当在本次运行后回填。

预留 **14 小时**连续 GPU 窗口，夜间运行。

## 磁盘预算（位置已改变）

中间数据现在放在 **WSL 的 ext4 磁盘**（`GSDB_SCRATCH_ROOT`，默认 `$HOME/gsdb-scratch`），不再占 D 盘。`work/<run-id>` 在项目内是一个指向 ext4 的符号链接。

| 项目 | 位置 | 预算 |
| --- | --- | ---: |
| 工作目录（投影、遮罩、金字塔、COLMAP） | ext4 | 约 22 GiB（基准 4.2 GiB × 4.75） |
| **训练 checkpoint（10 个）** | ext4 | **约 20–45 GiB** |
| 发布产物（PLY、预览、缩略图） | D 盘 | 约 1.5–3 GiB |

checkpoint 是新增的大头：基准单个 checkpoint 是 **1.08 GiB**（878,467 个高斯），现在默认每 10,000 步保留一个共 10 个。本次高斯数量预计更多，按 2–4.5 GiB 一个估算。

- **ext4 需要 ≥ 80 GiB 空闲**（实测当前 903 GiB 可用，充裕）。
- D 盘只需为发布产物留出空间，不再需要 50 GiB。
- 若 ext4 空间紧张，把 `steps_per_save` 调大到 20000（保留 5 个）即可减半；这是仪表参数，不影响训练结果也不进配置哈希。

## 风险与处置

- **致密化放大后的显存**（本次最大风险）。基准训练峰值 8,847 MiB / 16,376 MiB。71k 步致密化会产生远多于基准的高斯，显存与每步耗时都会上升。若触发 OOM，流水线按既定逻辑用 `downscale_factor: 2` 重试一次；先保留失败日志与资源指标。**建议在第一个 checkpoint（10,000 步）落盘后先看一眼显存曲线和高斯数量**，不要等 6 小时后才发现问题。
- **mapping 超线性**。若 mapping 超过 6 小时仍未结束，不要中断——它没有中间产物，中断等于全丢。先确认进程仍在推进（日志 `Registering image` 在增长）。
- **fallback 会显著延长总时长**。同帧跨视图匹配并入主流程后，按视图目录裂成多组件已经不是常规触发原因（基准从 8 个组件、覆盖 0.32 变成 1 个组件、覆盖 0.988），所以 fallback 触发概率明显降低。但真触发了要按"额外一天"预留，不要算进 9–14 小时。
- **单场景覆盖范围大**。README 的既定原则是长素材应拆成空间连续的街段。本次选择不拆、改为放大致密化窗口，属于明确取舍：省下 4 倍训练成本，代价是这个组合尚未验证。若验收发现后段区域欠收敛，应新建 run 或改为拆段，**不要覆写本次 run**。

## 验收与交付

1. 输入校验通过：2:1 全景 MP4、哈希与 capture 清单一致。
2. 遮罩 QA 通过，人物、摄影者与自拍杆邻近区域没有明显漏遮罩。
3. 主重建达到注册率与最大连通模型覆盖阈值（均 ≥ 0.70），rig 中心分布检查通过。
4. **发布坐标系检查通过**：QA 报告中 rig 重力偏差 p95 < 5°、发布后相机高度跨度占比 < 10%、位姿归一化峰值 ≈ 1.0。
5. **外围高斯剔除比例合理**（基准 2.05%）。明显偏高（接近 5% 上限）应先人工确认再接受。
6. 训练完成，资源指标、高斯数量、**评估曲线**与 `metrics.train.densification` 已写入 run manifest。
7. 导出物含 `artifact.yaml`、`splat-yup.ply`、缩略图、预览视频，以及三个能互相对齐的坐标文件（`transforms.json`、`transforms-colmap.json`、`dataparser_transforms.json`）。
8. **人工在查看器中确认**：场景正立、相机落在场景内成连续轨迹、远处浮点球消失、街道本体与远景建筑没有被误删。指标不能替代这一步。
9. 人工复核通过后 `gsdb qa approve`，再提交 Git 并通过 Git LFS 推送 PLY。
